**Problems you can document and explain — these are the good engineering stories**

This is actually the strongest part of any good project doc. Here's what you genuinely faced and can explain:

**1. Metastability — the UART_RXD synchronizer**
The problem: UART_RXD changes asynchronously relative to CLOCK_50. If it changes near a clock edge, the flip-flop output is undefined for an unpredictable time. The fix: 2-FF synchronizer. This is a textbook FPGA engineering concept and shows you know what you're doing beyond just making it work.

**2. Mechanical switch bounce**
The `debounce` module exists because mechanical switches don't produce clean transitions — they bounce for 1–20ms. Without debouncing, one button press triggers hundreds of edge pulses, scrolling the display multiple segments or clocking AES multiple times. You solved it with a 20-bit counter (~20ms at 50MHz).

**3. Single-cycle pulse visibility**
`dbg_is_hex` fires for exactly 1 clock cycle = 20ns at 50MHz. The human eye needs ~10ms minimum to perceive an LED flash. 20ns is 500,000 times too fast. You solved it with the stretch register — reload `20'hFFFFF` (about 20ms worth of cycles) on each pulse, decrement until zero. Document this with the actual math.

**4. UART FSM getting stuck**
Without `default: state <= IDLE`, if the FSM ever lands in an undefined state (possible on power-on before reset settles, or due to noise), it would freeze forever. The `default` case is a 1-line fix with significant reliability impact.

**5. Hardwired reset to 1'b0**
Original design had `.rst(1'b0)` — the UART could never be reset, meaning any glitch at startup could corrupt the FSM permanently, requiring reprogramming. Changed to `.rst(reset)` and propagated through all levels.

**6. The `done` signal re-triggering the counter**
`clk_counter` resets on `done | reset`. Why `done` and not just `reset`? Because after encryption completes, if you press clk_btn again the counter would keep incrementing past 11, giving you wrong readings. `done` auto-resets it so the next encryption starts counting fresh from zero.

**7. Active-low 7-segment displays**
The DE2-115 seven-segment displays are active-low — a `0` turns a segment ON, not `1`. This is a common mistake. If you got garbled display initially and had to invert the encoding, document that.

**8. STA negative slack — but it doesn't matter**
The timing report shows negative slack on CLOCK_50. This looks like a failure but it's not — the AES combinational path (SubBytes → ShiftRows → MixColumns → AddRoundKey through the S-Box LUT chains) is too long for 50MHz. But your design uses a manual button clock, so the combinational path gets effectively unlimited time to settle between button presses. Document this honestly — it's a real trade-off between the non-pipelined iterative design and what a fully clocked 50MHz implementation would need.

**9. Key ROM loaded from file**
`$readmemh("key.txt", mem)` loads at synthesis time — the file path is relative to the Quartus project directory. This is a common gotcha when the project is moved to a different machine. Document where the file must be placed.
